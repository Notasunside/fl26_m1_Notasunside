## 1. System structure
M1 is split into a few different parts, where each part has 1 main job. The TextProcessor cleans up text and turns it into normalized tokens, as practiced during Quiz 1. The chunker takes documents and breaks them into smaller overlapping chunks. The CorpusIndex keeps track of which terms appear in which chunks and how often they appear. The RetrievalEngine uses that index to score and rank chunks for a search query, but the ContextBuilder takes those ranked results and fits as much useful text as possible into a token budget. Overall, I followed the lecture slides from class (the one with the chart that followed through the steps).

ProcessingCore is basically the arranger for all of those aforementioned pieces. When a workspace is rebuilt, it sends the documents through the chunker, stores the chunks, and builds the index. When a search event occurs, ProcessingCore passes the query and stored corpus information to the retrieval engine. If context is requested, it then takes the ranked search results and passes them to the context builder. This keeps each component focused on one responsibility instead of putting the whole M1 algorithm into one massive class.

## 2. Design decisions
Explain the principal data structures, interfaces, and ownership decisions in your implementation and why you selected them.


I used simple STL containers for most of the data. The chunks are stored in an std::vector because their order matters, all the while the corpus index uses maps to quickly connect terms to the chunks they appear in and to keep track of term frequencies. Each major class has a small interface focused on its own job, such as Chunker::chunk(), CorpusIndex::document_frequency(), and RetrievalEngine::search(). This matches the M1 requirement that the system shall be split into separate processing responsibilities instead of putting everything into one large class. For ownership, ProcessingCore owns the current processing state through its private Impl object. This includes the stored chunks, index, retrieval engine, and context builder. I chose this way because this keeps the public interface small and lets the internal implementation change. But it doesnt effect the rest of the program. Most functions pass data by const reference when they only need to read it, which avoids any unnecessary copies. On the other hand, rebuilt corpus data is created separately and then moved into place only once it is valid.

## 3. Correctness and consistency
Identify the important invariants or failure cases your design must preserve and explain how your design addresses them.

The important invariants my design must preserve start with the text being always normalized in the same way. Then, chunks must stay within the required size/overlap rules, and the index always matches the current set of chunks. Rebuilding the workspace completely replaces the old corpus s.t. stale chunks or term counts do not remain. Rebuilding the workspace completely replaces the old corpus so stale chunks or term counts do not remain. Duplicate document IDs are treated as an error, and I build the replacement state separately before swapping it in so a failed rebuild does not destroy the last valid corpus. I also made sure invalid or boundary cases behave predictably. 

Any missing terms or chunkIds return 0 where I thought it was required, and multi token frequency requests throw an exception. Additionally, a negative search result count throws std::invalid_argument. Search results use deterministic tie breaking. THe context builder also never goes past its token budget; if the last chunk does not completely fit, it truncates the chunka nd stops. Cases like these are important since the spec specifically calls out stale rebuild states, duped Ids, ranking consistence, and budget limits. 

## 4. Testing strategy
Explain what your tests cover and which risks or boundaries you considered most important.

My tests cover both the individual components and the full processing. To name an exhaustive list, I tested text normalization, chunk sizes and overlap, document and term frequency in the corpus index, retrieval ranking, context-budget truncation, rebuild behavior, duplicate document IDs, and invalid multi-term frequency requests. Also, I tested several components directly instead of only going through ProcessingCore, which helps show that each subsystem works by itself.
The boundaries I considered most important were the ones where the spec names very specific behavior, such as the 120-token chunks with 20-token overlap. They had to rebuild w/o leaving stale data, keeping the old corpus if a rebuild fails, and making sure context never exceeds its token budget allocated. I also included missing data cases. This involves looking up a term frequency for a chunk that does not exist. That test actually exposed a segmentation fault that the public tests did not catch, so it was useful for finding a real edge-case bug.

## 5. Alternatives considered
Discuss at least two plausible design alternatives and why you did not choose them.

One alternative I considered at first was putting most of the M1 logic directly inside ProcessingCore. That would have been simpler at first because there would be fewer classes to deal with, but it would also make ProcessingCore responsible for normalization, chunking, indexing, ranking, and context building all at once. I was unsure if it would meet testing requirements, in that, I thought I would not be able to show those things without Processing Core. I did not choose that because it would make the code harder to test and maintain, and it would go against the assignment’s intention for a multi component design. One other alternative was rebuilding the existing corpus state in place instead of creating a new replacement state first. This way, I would use a little less temporary storage, but if something failed halfway through (such as detecting duplicate document IDs) the old valid corpus could be partially overwritten. I chose to build the new state separately and only replace the old state after the rebuild succeeds, because that makes the failure behavior safer and matches the spec’s requirement. A failed rebuild leaves the previous corpus unchanged.
